How DEFLATE works

The format inside gzip, zlib, PNG and ZIP is two simple ideas stacked on top of each other. First remove the repetition, then remove the skew. This page builds each one up, step by step, from a single 35-byte string.

  • DEFLATE makes two separate savings. LZ77 replaces each repeat with a short (length, distance) pointer back to an earlier copy. Huffman coding then gives common symbols short bit patterns and rare ones long patterns.
  • It matters because nearly everything uses it: gzip and zlib, PNG images, ZIP files, and Content-Encoding: gzip on the web.
  • The common misconception is that the Huffman tree travels with the data. It doesn't. Only the code lengths are sent, and the codes are rebuilt from them by counting.

A question to start

How do you make abracadabra abracadabra abracadabra smaller without losing a single letter?

Stored as plain bytes it takes 35 bytes, or 280 bits. Two things about it are wasteful. The same 11 letters appear three times, and the letter a makes up almost half of the text while c and d appear once per word. A good compressor should exploit both.

Guess before you read on: compressed as a gzip file by zlib at its best setting (level 9), how many bytes do these 35 take?

33 bytes. That looks like almost no saving, but 18 of those bytes are the gzip wrapper: a 10-byte header, then a CRC-32 and the original length (8 bytes) at the end. The DEFLATE stream inside is 15 bytes, 43% of the input. By the end of this page you will have taken it apart bit by bit, and seen an encoder that does it in 13.

Two ideas, stacked

DEFLATE runs two stages, and each removes a different kind of waste. LZ77 turns the bytes into a shorter list of tokens: a literal byte, or an instruction to copy earlier bytes. Huffman coding then writes each token with as few bits as its frequency allows.

The two stages are independent, and each is useful alone. A file of random English words has little exact repetition but plenty of skew. A file of one byte repeated is all repetition. DEFLATE needs both because real data has both.

LZ77: say it once, then point back

Read the input left to right. Keep everything already read in a sliding window (DEFLATE's holds the last 32,768 bytes). At each position, look for the longest run of upcoming bytes that already appears in the window. If it is at least 3 bytes long, emit a back-reference: copy length bytes, starting distance bytes back. Otherwise emit the byte itself as a literal.

Start with nothing. The cursor is at the first byte and the window behind it is empty, so there is nothing to point back to.

Seven literals. None of a b r a c a d starts a run of 3 bytes seen before, so each one drops out of the input as a literal token. The window grows behind the cursor.

A match. The next four bytes, abra, already appear 7 bytes back. Any run of 3 or more is worth replacing, and this one is 4 long.

Emit (4, 7). The four bytes collapse into one token: copy 4 bytes from 7 back. Four letters cost one token.

The space is new, so it goes out as a literal.

A long match that overlaps. Everything that is left, 23 bytes, repeats what started 12 bytes back. Only 12 bytes lie between the source and the cursor, so the copy runs into its own output.

Emit (23, 12). The decoder copies one byte at a time, so by the time it needs byte 13 of the copy, it has already written it. 35 bytes are now 10 tokens.

Overlap is not a corner case. It is how LZ77 encodes runs: aaaaaaaa is the literal a followed by (7, 1), "copy 7 bytes from 1 back".

Huffman: short codes for common symbols

Eight bits per letter is fair only if every letter is equally likely. In abracadabra the counts are a×5, b×2, r×2, c×1 and d×1, so a should get the shortest code. Huffman's algorithm finds the best codes for known counts, and it is greedy: repeatedly join the two rarest things.

Here the symbols are the letters themselves, to keep the tree small. DEFLATE runs the same algorithm on the output of LZ77 instead, as the join below shows: on counts of literals, lengths and distances, not of raw bytes.

Count each letter. At 8 bits a letter, the 11 letters of abracadabra cost 88 bits.

Line them up, rarest first. Each letter is now a leaf, weighted by its count.

Join the two rarest: c and d, 1 each, become a node of weight 2.

Again. Three things now weigh 2: b, r and the new node. Join any two. Here b and r make 4.

Again: 2 and 4 make 6. Only a (5) and this node are left.

The last join makes the root, 11, which is every letter. The common a joined last, so it ends up nearest the root.

Read the codes. Label every left branch 0 and every right branch 1. A letter's code is the path from the root to it. The total falls from 88 bits to 23.
At the second join, three nodes tied at weight 2. Join a different pair and you get a different tree. Does the total change?

No: it is still 23 bits. Join c+d with b instead, and the code lengths become a 1, r 2, b 3, c 4 and d 4. The tree is different, but 5×1 + 2×2 + 2×3 + 1×4 + 1×4 = 23 as well. Huffman's algorithm gives an optimal code, not the optimal code. That ambiguity is exactly what DEFLATE removes next.

Send lengths, not trees

The decoder needs the same codes as the encoder. Sending the tree would cost bits, and as the question above shows, many trees are equally good. DEFLATE fixes one rule for turning code lengths into codes, called the canonical Huffman code, so a block only has to send one small number per symbol.

Start from the tree. It gave a the code 0 and the others 100, 101, 110 and 111, in the order of its leaves.

Throw the codes away. Keep only each letter's length. This is all a DEFLATE block sends.

Sort by length, and alphabetically within a length.

The first code is all zeros. a gets 0.

Count up, then shift. Add one (1), then append a 0 for each bit of extra length: b gets 100.

Count up within a length. c, d and r get 101, 110 and 111. The decoder runs the same rules on the same lengths, so it gets the same codes without ever seeing a tree.

These are not the tree's codes, but they have the same lengths, so they cost the same 23 bits. Counting up keeps the code prefix-free: every 3-bit code starts with 1, and the only 1-bit code is 0.

How the two ideas join

The two stages meet once per block, always in this order:

  1. LZ77 turns the block's bytes into tokens: literals and (length, distance) copies.
  2. Map every token to symbols from two alphabets, described below. This is the join.
  3. Count the symbols and build two Huffman codes from the counts: one for literals and lengths, one for distances.
  4. Write the block: its header (for a dynamic block, including the two codes), then each token's symbols as Huffman codes, each followed by its extra bits, then the end-of-block code.

So Huffman coding never sees the raw bytes, or the tokens themselves. It counts and codes the symbols LZ77's output maps to, while the extra bits travel alongside, uncoded. The join is therefore a choice of alphabet for everything LZ77 can produce.

The obvious alphabet would give every possible value its own symbol: b0–b255 for the bytes, eob, w3–w258 for the lengths and d1–d32768 for the distances, 33,281 symbols in one code. DEFLATE does not do that. Its alphabets are drawn below, all 316 symbols. Pick something LZ77 can produce and see which symbol it becomes.

The two changes, one at a time:

  1. A length or distance is a range symbol plus extra bits. Length 23 is not a symbol of its own. It is symbol 270, which means "a length from 23 to 26", followed by 2 plain extra bits, 00, that pick 23. The extra bits are written as they are, not Huffman-coded. Short lengths (3–10) and distances (1–4) still get exact symbols, because they are the most common.
  2. Distances are coded separately. The bytes, the end of block and the length ranges share the first alphabet, so one code tells the decoder whether a literal or a copy comes next. A distance always follows a length, so the decoder always knows to read it with the second code.

The join, token by token

Here is the mapping applied to the ten tokens from the window figure, and then the codes that turn the symbols into bits.

Start from LZ77's output: eight literals and two back-references.

A literal is its own symbol. The byte a (97) is symbol 97 of the literal/length alphabet, which runs from 0 to 285. All eight literals map this way.

A back-reference becomes two symbols. Length 4 is symbol 258 of the same alphabet. Distance 7 is code d5 of a second, distance alphabet; d5 covers distances 7–8, so 1 extra bit follows to pick 7. (23, 12) becomes 270, covering lengths 23–26, with 2 extra bits, then d6, covering 9–12, with 2 more.

The block must end. Symbol 256, end-of-block, comes from the literal/length alphabet, so it sits among the literals and lengths and gets a code like them.

Huffman codes turn symbols into bits. Each symbol is replaced by its code from its own alphabet's table. This block uses the fixed tables: 8 bits per literal, 7 for symbols 256–279, 5 per distance code. Extra bits go out as they are, uncoded. With the 3 header bits that is 103 bits, the number in the first figure.

The decoder's inner loop runs the join backwards. Its two tables are the two alphabets:

while True:
    sym = read_code(lit_len_table)    # literal, length or end
    if sym < 256:
        out.append(sym)               # a literal byte
    elif sym == 256:
        break                         # end of block
    else:
        i = sym - 257
        length = LENGTH_BASE[i] + read_bits(LENGTH_EXTRA[i])
        d = read_code(distance_table) # always follows a length
        distance = DIST_BASE[d] + read_bits(DIST_EXTRA[d])
        for _ in range(length):       # byte by byte: may overlap
            out.append(out[-distance])

Three kinds of block

A stream is a series of blocks. Each block starts with 3 header bits: BFINAL (1 if this is the last block) and the 2-bit BTYPE, which says where the codes come from. Two bits allow four values, and only three are used:

The values of BTYPE. Header fields are read lowest bit first, so the bits arrive in the opposite order to how the value is written.
BTYPEArrives asBlock
000, then 0stored: raw bytes, no compression
011, then 0fixed Huffman codes, set by the RFC
100, then 1dynamic Huffman codes, sent at the start of the block
111, then 1reserved: invalid, and a decoder must reject the stream (zlib reports "invalid block type")

Stored (00)

No compression: up to 65,535 raw bytes after a 4-byte length and its complement.

  • Caps the cost of incompressible data at 5 bytes per 64 KiB
  • No saving at all

Fixed Huffman (01)

Codes set by the RFC: 8 or 9 bits for a literal, 7 or 8 for a length, 5 for a distance.

  • No table to send
  • Wins on short inputs
  • Ignores this data's skew

Dynamic Huffman (10)

Codes built for this block's own counts, sent as code lengths at the start of the block.

  • Removes the skew too
  • Usually wins once a block holds more than a few dozen bytes of text
  • The table costs tens of bytes

Any input can be written as any of the three, and every one is valid: a decoder accepts whichever it gets. Which one wins is a sum, not a rule. The encoder works out the exact size of each kind for every block (zlib ends a block after about 16,000 symbols) and writes the smallest. Tiny blocks come out fixed because a code table costs more than it saves: for the paragraph in the chart, zlib 1.2.12 switches from fixed to dynamic once the text is 74 bytes long.

Go deeper: why are the fixed codes 7–9 bits long?

A prefix code has a budget. A code of L bits uses up 2−L of all possible bit patterns, since nothing else may start with it, and the shares can't add up to more than 1. The fixed code must cover 288 symbols without knowing which are common, and spread evenly that is about log2 288 ≈ 8.2 bits each. The RFC spends the budget exactly:

SymbolsCountBitsShare of the budget
bytes 0–143 (all of ASCII)1448144 / 256 = 0.5625
bytes 144–2551129112 / 512 = 0.21875

The 7-bit codes for end-of-block and common lengths are paid for by making the upper half of the byte values, rare in text, cost 9 bits. Only a code fitted to the data can make a common symbol short, by making rare ones longer: that is what a dynamic block's code does.

Compressing the code lengths

A dynamic block opens with up to 316 code lengths, one per symbol of both alphabets. Sent as 4-bit numbers that would be about 160 bytes, more than many blocks save. So DEFLATE compresses the lengths too, with a third, smaller Huffman code.

  1. Count the alphabets. HLIT and HDIST, plain 5-bit numbers, say how many literal/length and distance codes follow, so unused symbols at the top cost nothing.
  2. Run-length the lengths. The sequence of lengths is written with 19 symbols: 0–15 are a length, 16 repeats the previous length 3–6 times, 17 and 18 write a run of 3–10 or 11–138 zeros. Like a length symbol, each run symbol is followed by plain extra bits that give its count: 2 bits after 16, 3 after 17 and 7 after 18. Long runs of unused byte values become one symbol.
  3. Code those symbols. The 19 symbols get their own canonical code, whose lengths come first, as plain 3-bit numbers, in the fixed order 16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15. HCLEN (4 bits) says how many are sent. The order puts the lengths that are usually unused last, so they can be left off.

For the 381-byte paragraph in the chart, zlib's whole header (HLIT = 270, HDIST = 17, HCLEN = 16, then the lengths) is 352 bits, about 44 bytes. That is the price of the table, and the paragraph is long enough to repay it.

Everything in the stream that isn't a symbol

A DEFLATE stream is mostly Huffman codes, but not entirely. Bits are written in two ways, and a decoder must know which kind comes next:

  • A Huffman code is read one bit at a time, most significant bit first, because the decoder walks down the code tree as each bit arrives.
  • Everything else is a plain number of a fixed, known width, read lowest bit first. Each byte of the stream fills from its lowest bit up, so a plain number's bits arrive in the order they are packed.

Everything else in the stream is a Huffman code: the literal/length and distance symbols, and, inside a dynamic block's header, the code-length symbols. The worked example's 119 bits show both kinds side by side in the bit walk.

The block header. BFINAL is 1, so this is the last block. The next two bits arrive as 1 0, lowest first, so BTYPE is binary 01: the fixed Huffman codes (see the BTYPE values). For 35 bytes, a dynamic table would cost more than it saves.

Eight literals, 8 bits each. In the fixed code, bytes 0–143 are 00110000 plus the byte, so a (97) is 10010001. That is no shorter than the raw byte, 01100001: the fixed code isn't fitted to this text, so it gives every byte from 0 to 143 the same 8 bits (why). This block's whole saving comes from LZ77's two copies. Notice also that zlib wrote the second a of abra as a literal.

A back-reference, (3, 7). Length symbol 257 means 3, with no extra bits. Distance code 5 covers 7–8, and its one extra bit, 0, picks 7. zlib copied bra where the window figure copied abra: 13 bits for 3 bytes.

Two more literals: the space (32) and another a.

The long, overlapping copy, (22, 12). Symbol 269 covers lengths 19–22, and the extra bits 11 add 3: length 22. Distance code 6 covers 9–12, plus 3: distance 12. 16 bits stand for 22 bytes.

Only 12 bytes lie between the source and the destination, but the copy is 22 long. Watch the output: the decoder copies one byte at a time, so when it reaches byte 25 it reads byte 13, which this same copy wrote 12 steps earlier. Every byte it reads already exists by the time it needs it.

End of block. Symbol 256 is seven zeros in the fixed code. That makes 119 bits; one more bit of padding fills the 15th byte.

Why is zlib's version bigger than the figure's?

zlib wrote 119 bits; the parse in the window figure needs 103. DEFLATE fixes how to decode, not how to encode: any token stream that rebuilds the input is valid. zlib's hash chains use position 0 as their "no match" marker, so zlib never copies from the very first byte of a stream. Both of its copies here would have started there, so each starts one byte later, after an extra literal a: 16 bits lost. On real files, zlib's smarter match choices win by far more. Other builds choose differently again: Chromium's fork of zlib, in Chrome and in Node's official binaries, writes 17 bytes for this string.

Why decoding is serial

The output is dense: there are no separators and no index. A code's length is known only once it has been decoded, so the decoder cannot find where symbol n + 1 starts without decoding symbol n. Back-references add a second chain: a copy reads bytes that earlier tokens wrote.

That is why a gzip file is decompressed by one core, front to back, however many cores the machine has. Getting around it, for example to decode on a GPU, means finding where blocks start without decoding what comes before, and resolving copies whose sources aren't decoded yet. A later series here takes that on; nothing on this page depends on it.

Edge cases

Overlapping copies
Allowed and common: distance 1 with length 258 repeats the previous byte 258 times. A decoder must copy byte by byte, not with a block copy, or it reads bytes that haven't been written yet.
The longest match
258 bytes, with its own symbol (285) and no extra bits, so with the fixed codes a long run costs 13 bits per 258 bytes. 258 = 255 + 3: a length fits in a byte once the minimum of 3 is subtracted.
End of block
Symbol 256 ends every Huffman block, even the last. It needs a code, so it counts as a symbol when the tree is built.
Empty input
zlib writes 2 bytes, 03 00: a final fixed block holding only the end-of-block code.
Incompressible input
Stored blocks cap the overhead at 5 bytes per 65,535. A large file of random bytes grows by under 0.01%; the 1 KiB in the chart grows by 0.5%.
